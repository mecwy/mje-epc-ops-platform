# ADR-0003：跨模块最小权限——授权上下文、模块出口与投影

日期 2026-10-01。状态：**候选**（送 Codex 技术审核；通过后随 A7 首个切片生效）。编号接续私有档案的 ADR-0001（原架构 v0.1，只读原件）与 ADR-0002（Phase 0 实施细化）；本文件是公开仓库中的第一份 ADR。

依据（业务规则已由 Owner 确认，本 ADR 只定执行方式）：DG-05 / DG-06 共用设计段 `authorized-projection.md`（随 DG-06 v0.5 确认，K20）、授权管理最低政策 `authorized-projection-policy.md`（Owner 2026-10-01 默认政策 P1–P3 与四个触发条件）、独立技术评议（2026-10-01，Codex）、OD17 / OD18 / OD20、经验 L22。三份设计文件在私有档案 `docs/design/dg06-opportunity/`；本 ADR 不复制其中的业务字段表，只引用条款号。

## 1. 背景

- 现状（`packages/domain/src/store-kit.ts`）：每个请求在 `inTransaction` 内从验证后的 Entra 身份找到 `LoginAccount`，要求至少一条有效 `Membership`，得到 `Actor{orgId, accountId, personId}`，再按项目用 `projectAccess` 判 `write`（PROJECT_MANAGER）或 `read`（EXECUTIVE_READER，按项目或全组织）。现场设备（`FieldDevice` 令牌）是第二类主体，范围固定为一个项目、一个自然人，工头身份由 `CrewAssignment` 在决策时刻判断。
- 已有的投影雏形：`reader-view.ts` 对只读账号只给已提交版本（OD18），不给照片精确坐标（OD20）；`/days` 对只读账号不列草稿日；照片跨项目一律 `NOT_FOUND`，不区分“无权”和“不存在”；图片字节只经服务端流式转发，没有 SAS 或预签名链接。
- 缺口：这些规则分散在各 store 的 SQL 和 if 分支里，没有一处声明“哪个读取面给谁看什么”，也没有机械检查能发现新入口漏了投影。DG-05 与 DG-06 两个设计包在写入路径上两次（第三次在汇总/条款文字）漏掉“方向 × 范围”的反向检查（L22）。A7 要做多项目首页与项目状态，读取面从单项目扩到跨项目聚合（状态计数、过期天数、缺报、未关闭上报、关注项），即使不含金额，也会通过计数与派生提示泄露受限事实。
- 边界：不建通用权限引擎、不建授权管理界面、不设计分包商账号流程（政策 §3 的触发条件出现后另开设计包）。

## 2. 决定

### D1 授权上下文（AuthorizationContext）

- 由服务端在事务内、从验证后的身份与会员关系建立；客户端提交的 `orgId`、角色、授权版本一律不信任（AGENTS 已有规则，此处落为结构）。
- 字段：`principal`（`account` 或 `fieldDevice`）、`orgId`、`accountId`（设备主体为 null）、`personId`、生效中的授权列表、`authzVersion`（该账号授权集的单调版本，见 D6）、决策时刻 `decidedAt`（数据库时钟，不用主机时钟）。
- 每一条授权 = `{能力, 范围, 方向, 有效期, 依据, 授予人/系统}`（设计段 §3）。能力带模块命名空间（`report.view`、`report.write`、`project.status.write`、`contract.amount`…），同名动作在不同模块是不同能力。
- 过渡：现有 `Membership.role` 在本 ADR 下视为**隐式授权记录**——`PROJECT_MANAGER@project` ⇒ `report.*`、`issue.*`、`photo.*`、`field.admin.*`、`project.status.write` 于该项目；`EXECUTIVE_READER@org|project` ⇒ 各模块 `*.view` 且只见已提交版本，另加 `issue.reply`。A7 不新建授权表；首次需要显式授权记录的模块（DG-05 合同）在其首个 PR 追加表，字段按政策 §2 的最小结构（账号 / 会员 / 自然人分离、授权 id、能力、范围对象、方向、期间、授予与撤销事件、来源与模板版本、代岗/代录关系）。
- 独立性判断按 `personId`（自然人）与交易关系，不按账号。设备主体不能持有账号主体的能力；两类主体走同一套出口。

### D2 模块出口与投影 DTO

- 原始实体、Prisma 行和仓储只在所属模块内部可见。跨模块读取只有一种形式：所属模块导出 `xxxReader.forContext(ctx)`，返回**投影 DTO**，DTO 里每个字段都在该模块的字段分层表登记（D3）。
- 控制器、首页/收件箱聚合、导出（DG-08）、Worker/定时任务都只消费投影；不得直接 `SELECT` 另一模块的表做汇总。关联对象由其所属模块投影（设计段 §6）：日报引用的问题由 issue 模块投影，项目卡片引用的最新状态由 project-status 模块投影。
- 机械边界，三件事缺一不可：
  1. 依赖规则：`packages/domain` 内按模块目录划分（A7 起新代码进 `report/`、`issue/`、`photo/`、`field/`、`project/` 子目录，旧文件逐步迁，不在本 ADR 一次搬完），ESLint `no-restricted-imports` 禁止跨目录引用 `*-store.ts` 与 `*.repo.ts`，只允许引用 `*-reader.ts` / `*-commands.ts` 导出的接口；
  2. 入口清单：`packages/domain/src/authz/surface.ts` 列出每个 HTTP 路由与 Worker 入口对应的 `{读取面或命令, 所需能力, 范围来源, 方向, 投影函数}`；一个单元测试枚举 NestJS 控制器的全部路由，未登记即失败；
  3. 字段清单：每个投影 DTO 的字段在 `authz/fields.ts` 分层（结构与身份 / 公开摘要 / 金额 / 受限文字 / 条款 / 原件 / 坐标 / 草稿事实）；类型级检查保证 DTO 的键集合 ⊆ 已分类键集合，新字段未分类即编译失败。
- 行级安全（RLS）继续保护租户隔离，不承担字段级权限。

### D3 字段与派生信息

- 字段分层按设计段 §4；A7 新增两层：**草稿事实**（OD18：只读主体在提交前连存在都看不到）与**坐标**（OD20：只读主体只见“有/无位置”与声称精度）。
- 投影按字段语义作用于所有嵌套值：当前值、历史旧值/新值、修订快照、事件前后快照、附件元数据、错误与冲突响应（`VERSION_CONFLICT` 携带的“现在是 Y”同样经投影）。当前看不到的，历史里也看不到（设计段 §5）。
- 汇总只消费投影后的对象；读者看不到的对象，其状态不得改变读者看到的任何数字、分类、排序或标记（DG-06 R4-1）。做法：聚合函数的输入类型就是投影 DTO，不接受原始行。
- 不可反推：读者看不到的分量，不进入任何可见合计、差额、比例；该合计标“含受限项”并隐藏数字。
- 存在性不泄露：对无查看权的对象，响应与“不存在”逐字节相同（现有照片规则推广到所有模块）；列表不列、计数不计、`/days` 不出现。
- 受限自由文字整段遮蔽为固定提示，不按关键词删改；无法判断是否含受限内容的文字按受限处理。
- 系统提示（OD17 规则 3：日均低于基准、节点预计延后、缺报、未关闭上报）是派生信息，只能由投影后的已提交事实计算；对只读主体，派生提示不得暗示草稿存在（例如“今天尚未填写”与“今天无记录”对只读主体必须同一表述）。

### D4 写入按操作声明

- 每个命令在 `surface.ts` 声明：所需能力、目标方向、范围来源（路径参数 / 载荷中的对象 id / 关联对象）、前提能力、影响字段（含连带字段）、是否属金额写入。不得统一套“维护 + 全部读取能力”。
- 范围检查做两次：提交前（对象当前所属范围）与提交后（命令结果所属范围），防止把对象移到无权项目、借状态变更影响受限字段。
- 基准：每个命令改变的字段都带基准值，连带字段同样（例如完整的获授记录按修订号、当前主路径）；任一不符整体冲突、什么都不写；缺基准即拒绝。冲突响应经投影。现有 `expectedVersion` 继续作为聚合级基准；子记录修订号在需要时追加，不为每个字段单建参数。
- 只读主体的唯一写入是 `issue.reply`（OD16 第 7 条）；A7 的 `StatusNote` 同属此类。

### D5 撤权、事务与重放

- 授权判断与写入在同一事务、同一快照；`authzVersion` 在读取授权集时取出，提交前以 `SELECT … FOR SHARE` 复核未变，变了则整体拒绝（`AUTHZ_CHANGED`），不依赖客户端带来的旧授权基准。
- 撤权（`Membership.activeUntil`、将来授权记录的撤销事件）下一次请求即生效；现场设备令牌沿用 `memberUntil` 与高水位时钟机制（A6a）。
- 幂等重放：先按当前上下文做与首次相同的授权检查，再回放存储响应；无权即当前拒绝，不回放旧的敏感响应。回放体同样经投影（存储的是首次响应，撤权后的字段可见性可能已变）。
- 排队与后台任务（A8 重传、DG-08 导出、清理 job）在执行时与领取结果时各重新授权一次；队列项只存引用，不存投影结果。
- 附件：继续只经服务端流式转发，不签发预签名链接；若将来引入，须在此 ADR 追加 TTL 与残余访问声明，不得声称“下一请求即撤权”。

### D6 验证契约（经验 L22 的机械化）

- 规则表就是 `surface.ts` + `fields.ts`。测试生成器从规则表展开 TEST 场景：
  - 方向：匹配 / 反向 / 全部；
  - 范围：覆盖 / 不覆盖 / 部分覆盖 / 多项目共享 / 未分配；
  - 授权：有效 / 撤销 / 到期 / 缺前提 / 设备主体；
  - 路径：详情、列表、首页聚合、汇总、历史、关联对象、导出、下载，以及每个写入入口。
- 每个拒绝场景配一个正向对照。**期望值独立于生产授权函数**：生成器自带一份用枚举写死的最小解释器（可见键集合、允许/拒绝），与实现对照，不调用实现自证。
- 两类性质检查补足枚举：只改读者不可见的状态或数值，读者看到的输出逐字节相同；只改方向或范围使其越权，写入被拒且无副作用（无审计行、无版本递增、无出站任务）。
- 未建模维度（例如项目份额）在规则表标 `unmodelled`，生成器为其**不生成**用例并在报告列出，不记为通过。
- 每个落地 PR 必须含真实消费路径（至少一个控制器或聚合改为经出口读取）与负向证据；只合入无人调用的框架视为未完成。

### D7 并发基准类别

| 类别           | 最少覆盖                                                        |
| -------------- | --------------------------------------------------------------- |
| 直接修改值     | 金额、数量、日期、文字、值状态（空白 / 明确零 / 未知 / 不适用） |
| 完整复合记录   | 获授记录的金额、币种、税口径、来源、引用、依据、修订号          |
| 连带修改       | 当前主路径、计划有效性、结果、关联或分配关系                    |
| 决策依赖       | 判断本次动作是否允许的当前状态、有效份额、关联版本              |
| 授权与身份依赖 | 会员有效性、`authzVersion`；涉及独立性时的自然人与关系依据      |

### D8 落地顺序

1. **A7（首个切片，本 ADR 的生效条件）**：
   - `report` 模块出口：`projects / days / day / revision / plan / items` 全部改为经 `reportReader.forContext(ctx)`，`reader-view.ts` 并入其中；`lagSuggestions` 与计划提示只消费投影；
   - `project-status` 模块（新）：`ProjectStatusUpdate` / `StatusNote` 的命令声明与投影；多项目首页与“需要您关注”收件箱是**消费方**，只拼投影 DTO；
   - OD18 全路径服务端强制的负向集成测试：只读主体对 `/days` 计数、首页卡片、缺报提示、关注项计数、`VERSION_CONFLICT` 响应均不见草稿事实；
   - `surface.ts`、`fields.ts`、路由枚举测试、依赖规则，先只覆盖 report / issue / photo / project-status 四个模块；field 模块登记入口但保留现有实现；
   - 核对 `idempotent()` 各调用处的顺序，使授权检查先于回放；
   - C19 / C20（OD22）：提交时冻结节点主数据与主工作项键；快照对草稿只冻结状态。
2. **A8**：离线缓存按主体 + `authzVersion` 隔离；重连后先刷新上下文再放行重传；重传队列项只存命令与基准。
3. **DG-05 首个 PR**：追加显式授权表与授予/撤销事件；接入合同方向、份额、条款与金额策略；DG-06 实现时逐条独立复核 §22 的 R4-1 / R4-2 / R4-3。
4. 其后每个模块的新读取面与新命令必须先登记 `surface.ts`，否则 CI 失败。

## 3. 不采用的方案

| 方案                                   | 不采用的原因                                                                        |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| 通用权限引擎 / 策略语言 / 独立授权服务 | 各模块会用例外旁路；AGENTS 禁止无 ADR 引入新基础设施；A7 只需要四个模块的最小契约   |
| 只在控制器入口鉴权，投影交给前端隐藏   | 首页聚合、历史、附件、冲突响应会旁路；前端隐藏不是边界（OD18 已证明需要服务端强制） |
| 用 RLS 做字段级权限                    | RLS 只保护行与租户；字段、派生数字与历史需要应用层投影                              |
| 现在就建授权管理界面与分包商流程       | 政策 §3：四个触发条件未出现；人员未定时设计价值低                                   |
| 每个字段独立客户端基准参数             | 聚合版本 + 子记录修订号已覆盖 D7 五类；逐字段参数增加载荷又不增加保护               |

## 4. 后果

- A7 的工作量增加一个基础层（出口、清单、生成器），但 OD18 服务端强制与首页聚合本来就需要同样的读取控制；不做这一层，A7 的负向测试只能逐条手写。
- 旧 store 文件不一次搬迁；过渡期内 `*-store.ts` 同时承担命令与读取，只要求新入口经出口、旧读取面在 A7 内改完。
- 隐式授权（角色即授权）在 DG-05 之前继续有效；显式授权表引入后，角色映射改为迁移时生成的授权记录，不删角色字段。
- 本 ADR 不改变任何业务规则，不新增可见范围、授予权或代录行为；这些仍是 Owner 决定（政策 P1–P3）。

## 5. 验收

- 本 ADR：Codex 技术审核 APPROVE 或 APPROVE WITH NITS 且 nit 已修/已记录；文档 PR 预算 2 轮。
- A7 首个切片合并条件：D2 三项机械检查在 CI 生效并至少覆盖四个模块；D6 生成器对 report / project-status 的方向 × 范围 × 授权 × 路径矩阵全部通过，`unmodelled` 项列出；OD18 全路径负向测试通过；`pnpm check`、`test:report`、`test:issues`、`test:photos` 不回退。
- 测试通过不等于现场事实已核实，也不等于 AT/LR 应用验收通过（AGENTS）。
