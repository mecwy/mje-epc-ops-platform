## 2. 派生数字（服务端计算，只消费已提交快照与声明；从不改写声明）

| 数字               | 规则                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | 无法计算时                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 完成 %             | 取 T 前最新已提交快照；分子 = 该快照 `facts.cumulative[key]`，为空时取 `cumulativeCarry[key].value`（`CarriedCumulative {value, asOf}`，`report-rules.ts:460–464`）；分母 = 该快照冻结的主工作项 `designQty`。用现有 `pct()`（`report-rules.ts:67–71`，Decimal，1 位小数，半进）。**明确零分子可计算（0.0 %）**；只有分母为空 / 未知 / 不适用 / 0 或分子为空 / 未知 / 不适用才不可计算。累计 > 设计量照算并标“已超设计量”                                                                                                                     | 主工作项未设 → “未设主工作项”；不可计算 → “不可计算”，不显示 0 % |
| 状态过期           | 今天（工地时区业务日）− 最近声明的 `businessDate` > 7 天                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | 从未声明 → “未声明”，不是“过期”                                  |
| 低于基准           | 复用 `lagSuggestions`（逐日与当日基准比较，连续 3 天 < 80 %，无数据不算证据；已有未关闭 `progressLag` 问题或当日已忽略的工作项不再提示，`issue-store.ts:429–441`），按项目汇总为“N 个工作项连续 3 天低于基准”                                                                                                                                                                                                                                                                                                                                 | 无基准 → 不提示                                                  |
| 主工作项预计完成日 | D9：样本 = 近 7 个业务日里主工作项有已提交数字 `qty` 的日（`unknown` / `na` / 空不进样本；样本内主工作项键**或该项冻结的 `unit`** 与最新快照不同的日不进样本、且样本从其后重新开始（单位不同的数不相加）；`r` = 样本 `qty` 之和 ÷ 样本日数（Decimal）；剩余量 = 设计量 − 累计；剩余量 ≤ 0 → 显示“已达设计量”，不给预计日；`r > 0` 且剩余量 > 0 时预计完成日 = 今天 + ⌈剩余量 ÷ r⌉ 天；显示“按近 7 天观测日均（n/7 天样本）推算”，固定注：算术推算，不是延期结论（LR06）。只与**主工作项自身**的 `plannedDate`（若设）比较；不对其他节点做预测 | 样本为空、`r = 0`、累计或设计量不可计算 → 不提示                 |
| 日报缺报           | D4 / U10：对窗口内每个**已过截止**的业务日 `d`（截止时刻 `T_d` = `d` 在工地时区的 24:00，且 `T_d ≤` 请求时刻；当天未到截止不判）；取 `registeredAt ≤ T_d` 的最新应报期间版本；`d` 在其 `[fromDate, toDate]` 内且周几 ∈ `workdays` 才是应报日；应报日且 `T_d` 前无已提交版本（`Revision.submittedAt ≤ T_d`，时刻定义见 D11）= 缺报。`T_d` 之后登记的版本不影响 `d`（既不新增也不抹去义务）。不从 `DailyClose` 推断义务（写入才建行、读取不建行，`report-store.ts:183–200, 483`）。窗口 14 天（D8）                                             | 无任何 `registeredAt ≤ T_d` 的版本 → 该日不判                    |
| 未关闭上报         | `Issue.escalate = true` 且 `state` ∉ `CLOSED_STATES` 的条数                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | —                                                                |
| 近 7 天日报        | 近 7 个业务日中已提交的日数 / 7；每日一格：已提交 / 无记录（只读主体对草稿与无记录显示同一格，U6）                                                                                                                                                                                                                                                                                                                                                                                                                                            | —                                                                |

## 3. 授权与投影（ADR-0003 D8.1 首个切片；能力名、层名与 ADR 一致）

- 新模块 `project-status`（`packages/domain/src/project-status/`）：`projectStatusReader.forContext(ctx)`；命令 `declareStatus`、`addStatusNote`、`setPrimaryWorkItem`、`registerExpectation`。能力：`project.status.view`、`project.status.declare`、`project.status.reply`、`project.master.write`（ADR D1 表）。
- `report` 模块出口 `reportReader.forContext(ctx)`（A7-0a）：`projects / days / day / revision / plan / items` 与首页需要的“最新已提交快照摘要”都从这里读；`reader-view.ts` 并入。**C20 读者投影（A7-0c，有行为变化）**：对只读主体，所有读者路径（含历史 `revision`）把 `nextPlan.status ≠ 'confirmed'` 的 `nextPlan.rows` 投影为 `[]`——现状 `readerContent` 原样返回 `s.nextPlan`（`reader-view.ts:111`），历史快照里冻结了草稿行（`report-store.ts:438–441`）。存储的快照不改；加含草稿行的旧快照夹具。
- 首页与收件箱是**消费方**：`homeAggregator` 的输入是三个模块（report、issue、project-status）的投影 DTO，不读原始行；读者能看的项目 = 三个模块 `view` 的交集（ADR D8 表）；每个项目一张卡片 = `{project(结构与身份), latestStatus?, derived(§2), attention[]}`。
- 字段分层（`authz/fields.ts`）：声明的 `status / areas / 日期 / 序号 / needsSupport` = 结构与身份；`situation / recovery / supportNote / 回复 text` = **项目公开文字**（ADR D3）；派生数字只由已提交事实计算。
- **经理身份投影**（D3）：现 `Membership` RLS 只暴露调用者自己的会员（`202609280001:31–34`），只读账号读不到其他账号的 PROJECT_MANAGER 会员。新增 `SECURITY DEFINER` 函数 `project_managers_for_org()`（固定 `search_path`，无参数，按 `app.org_id` 过滤，返回 `(projectId, personId, displayName)`，只含 `activeFrom ≤ decidedAt AND (activeUntil IS NULL OR activeUntil > decidedAt)` 的 PROJECT_MANAGER 会员（与 `projectAccess` 同一谓词，`store-kit.ts:134`），经 `LoginAccount.personId` 映射到 `Person.displayName`），应用角色只有 EXECUTE；不扩大对 `Membership` / `LoginAccount` 行的可见性。只读角色的集成测试覆盖分组。
- 只读主体（EXECUTIVE_READER）：看项目卡片、概况、声明历史、回复；写入只有 `addStatusNote`。写入主体（PROJECT_MANAGER）：本项目的声明、主工作项、应报期间；也可回复。
- 存在性不泄露：无权项目的 `/projects/:id/*` 一律 `NOT_FOUND`（响应体除 `correlationId` 外相同）；首页只列有权项目；其他组织不可见（RLS + 出口双重）。
- 入口清单（`authz/surface.ts`）登记 §4 的每条路由（`concurrency` 与 `discloses` 字段按 ADR D4 / D3）；路由枚举测试覆盖 report / issue / photo / project-status。
- **锁顺序**（全部命令，ADR D5）：账号第一锁（`app_account_for_identity`，定义者函数）→ 授权（`projectAccess` / `projectWriter`）→ 幂等锁 → `Project` 行锁（§6）→ 资源锁（roster / DailyClose / 日锁，现有顺序）。A7-1a / A7-1b 依赖 A7-0b（账号锁与协议先落地）。

## 5. 时间

- `declaredAt` 用数据库时钟（`now()`）；`registeredAt` 用锁后的 `clock_timestamp()`（D11）；`siteTimezone` 随声明冻结；`businessDate` 由 `declaredAt` 按该时区换算；客户端不传时间。
- 过期、缺报、近 7 天都按工地时区业务日；今天 = 请求时刻在项目时区的日期。多项目首页里每个项目用各自时区。
- “每周一更新”只是提示（声明页顶部“上次声明 N 天前”），不强制。

## 6. 事务与并发

- **`Project` 行锁作为主数据的单一捕获点**：`declareStatus` / `registerExpectation`（分配 `n`）与 `setPrimaryWorkItem` / `saveItems`（主数据写入）取 `SELECT … FROM "Project" WHERE "orgId"=$1 AND id=$2 FOR UPDATE`；**所有产生修订的路径**——`submit`（含更正后的重新提交，`report-store.ts:892–912`）与 `noWork`（`report-store.ts:926–955`），两者都调用 `submitRevision`——在各自外层命令里、幂等锁之后、`rosterLock` 之前取同一行 `FOR SHARE` 并重新读取项目数据，然后在同一事务内读主工作项键、工作项与节点主数据并冻结（不在共享的 `submitRevision` 里取锁，否则锁会落在 roster / DailyClose / 日锁之后）——写入者被序列化在 share 锁之外，因此冻结的键与项元数据来自同一已提交状态（现状：提交前取项目行、回调里再读 items，`report-store.ts:892–900, 815–823`，两次读之间 items 可能变化）。`FOR SHARE` / `FOR UPDATE` 需要 `Project` 的列级 UPDATE 权限（§9 的 GRANT 提供）。
- 锁顺序见 §3；`Project` 行锁位于幂等锁之后、roster / DailyClose 锁之前；`saveItems` 现无锁（`report-store.ts:1326–1357`），A7-1b 为其加 `Project` 行锁（行为变化：同项目的 items 保存被序列化，登记）。
- 两个经理同时声明：一个成功、一个 `VERSION_CONFLICT`；两个声明 `expectedN` 相同而内容不同 → 幂等键不同、行锁串行、第二个冲突（负向测试）。并发“改主工作项 / 改工作项 vs 提交”与“… vs 今日无施工”两组受控测试：冻结的键与项元数据必须同属一个提交前或提交后状态。
- 触发器：三张只追加表禁止 UPDATE / DELETE（同 `foreman_report_revision_append_only`）。

## 8. 负向测试（集成，TEST 库；权限测试以 `mje_alpha_app` 执行，触发器测试以受控 TEST 角色执行；走 HTTP）

## 9. 迁移与回退

- 按切片追加迁移（每个只追加，已应用的不改）：A7-1a 状态两表 + 触发器 + RLS + GRANT（`SELECT, INSERT`）+ `Project` 列级 `UPDATE (version)`（§6 行锁所需的最小权限：`FOR UPDATE` / `FOR SHARE` 要求至少一列的 UPDATE 权限，现仅 SELECT，`202609280001:22`）；A7-1b `Project` 三列 + 列级 `UPDATE (primaryWorkItemKey, region, projectType, updatedAt, updatedBy)`+ `ReportItem.kind` CHECK 扩展 + `plannedDate` + 应报期间版本表；A7-2b `project_managers_for_org()`。
- **回退（保留数据，按 `infra/bicep/README.md` 的程序）**：旧镜像 = 引入该迁移的切片之前的 `main` 镜像（A7-1b 起有 milestone 不兼容风险）（命名具体 digest）。兼容性**有条件**：新表与新列旧代码不读；但一旦某项目创建了 `kind='milestone'` 的行，旧镜像的 `items()` 会把它读出并冻结进快照（`report-store.ts:286–292, 436`），旧 `SaveItemsCommand` 解析器拒绝该 kind（`contracts/report.ts:340`），该项目的工作项保存在旧镜像下失败——即**不兼容**。因此：先在应用层停入口并确认写入已停（缩到 0 不算停）；若尚无 milestone 行，用旧镜像并做读 / 渲染 / 写 / 提交四项核对后再开放；若已有，保持停写、前向修复，不回退镜像。保留迁移历史、新增表、授权 / RLS / 触发器、Revision、审计与 Blob；不 DROP。
