状态：**设计 r1，候选**（送 Codex 设计审核，预算 3 轮；通过后按 §10 切片实现）。本文件没有应用代码、迁移或契约；示例全部是合成 TEST 数据。

## 2. 派生数字（服务端计算，只消费已提交快照与声明；从不改写声明）

| 数字         | 规则                                                                                                                                                                                                                                     | 无法计算时                                                                  |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 完成 %       | T 前最新已提交快照中主工作项的累计（`cumulativeCarry` 或该日 `cumulative`）÷ 该快照冻结的 `designQty`，Decimal 运算，1 位小数，算术值                                                                                                    | 主工作项未设、累计或设计量为空 / 未知 / 不适用 / 0 → “不可计算”，不显示 0 % |
| 状态过期     | 今天（工地时区业务日）− 最近声明的 `businessDate` > 7 天                                                                                                                                                                                 | 从未声明 → “未声明”，不是“过期”                                             |
| 日均低于基准 | 复用 `lagSuggestions`（连续 3 天 < 基准 80 %，无数据不算证据），按项目汇总为“N 个工作项低于基准”                                                                                                                                         | 无基准 → 不提示                                                             |
| 节点预计延后 | 对每个有 `plannedDate` 且未记实际完成的节点：取主工作项近 7 天（只算有已提交数字的日）日均 r；`r > 0` 时预计日 = 今天 + ⌈(设计量 − 累计) ÷ r⌉ 天；预计日 > 计划日 → “按近 7 天日均预计延后 N 天”。固定注：算术推算，不是延期结论（LR06） | 近 7 天无数字或 `r = 0` → 不提示                                            |
| 日报缺报     | 按 D4：应报日（在期间内且为工作日）且 T 前无已提交版本的日数（近 14 天窗口）                                                                                                                                                             | 无应报期间版本 → 不提示                                                     |
| 未关闭上报   | `Issue.escalate = true` 且状态不在 `VERIFIED_CLOSED / CLOSED` 的条数                                                                                                                                                                     | —                                                                           |
| 近 7 天日报  | 近 7 个业务日中已提交的日数 / 7；每日一格：已提交 / 无记录（只读主体对草稿与无记录显示同一格，U6）                                                                                                                                       | —                                                                           |

提示与声明不一致（例如声明“正常”但有未关闭上报或预计延后）时**并列显示**，不改声明、不算分、不排序到例外组之外（U3）。

## 3. 授权与投影（ADR-0003 D8.1 首个切片）

- 新模块 `project-status`（`packages/domain/src/project-status/`）：`projectStatusReader.forContext(ctx)` 返回投影 DTO；命令 `declareStatus`、`addStatusNote`、`setPrimaryWorkItem`、`registerExpectation`。
- `report` 模块出口 `reportReader.forContext(ctx)`：`projects / days / day / revision / plan / items` 与首页需要的“最新已提交快照摘要”都从这里读；`reader-view.ts` 并入；`lagSuggestions` 只消费投影。
- 首页与收件箱是**消费方**：`homeAggregator` 的输入类型是三个模块（report、issue、project-status）的投影 DTO，不读原始行；每个项目一张卡片 = `{project(结构与身份), latestStatus?, derived(§2), attention[]}`。
- 字段分层（`authz/fields.ts`）新增：`project-status.*` 全部为“结构与身份”层（无金额、无受限文字；`situation / recovery / supportNote` 是声明者写给总监看的文字，按 U2 本来就对只读主体公开）；派生数字只由已提交事实计算（ADR D3 最后一条）。
- 只读主体（EXECUTIVE_READER）：看项目卡片、概况、声明历史、回复；写入只有 `addStatusNote`。写入主体（PROJECT_MANAGER）：本项目的声明、主工作项、应报期间；也可回复。
- 存在性不泄露：无权项目的 `/projects/:id/*` 一律 `NOT_FOUND`；首页只列有权项目；其他组织不可见（RLS + 出口双重）。
- 入口清单（`authz/surface.ts`）登记 §4 的每条路由；路由枚举测试覆盖 report / issue / photo / project-status 四个模块。

## 5. 时间

- `declaredAt` 用数据库时钟（`now()`），`businessDate` 由 `declaredAt` 按项目时区换算；客户端不传时间。
- 过期、缺报、近 7 天都按工地时区业务日；今天 = 请求时刻在项目时区的日期。多项目首页里每个项目用各自时区。
- “每周一更新”只是提示（声明页顶部“上次声明 N 天前”），不强制。

## 6. 事务与并发

- `declareStatus`：`SELECT … FROM "Project" … FOR UPDATE`（项目行锁）→ 读最新 `n` → 比对 `expectedN` → INSERT。两个经理同时声明：一个成功、一个 `VERSION_CONFLICT`（负向测试）。锁顺序：幂等锁 → 项目行锁；不与日报的 `lockReportDay` 同时持有（声明不碰日报表）。
- 触发器：`ProjectStatusUpdate`、`ProjectStatusNote`、`ReportingExpectationVersion` 禁止 UPDATE / DELETE（同 `foreman_report_revision_append_only` 模式）。
- 快照新增字段在 `submit` 的同一事务内读取主数据（与 `items` 同一时刻），不在提交后补写。

## 8. 负向测试（集成，TEST 库，`mje_alpha_app`，走 HTTP）

1. 只读账号：`POST status / primary-work-item / reporting-expectation` → `READ_ONLY`；`POST notes` 成功。
2. 有风险 / 已偏离缺任一必填 → `STATUS_FIELDS_REQUIRED`，无行写入、无审计。
3. 并发：两个声明同 `expectedN` → 一成功一冲突；冲突响应含当前最新声明且经投影。
4. 只追加：`UPDATE / DELETE ProjectStatusUpdate` 作为 `mje_alpha_app` 被触发器拒绝。
5. 过期：声明业务日 8 天前 → 卡片 `stale=true, staleDays=8`；7 天 → `false`（边界）。
6. 提示与声明并列：声明“正常”+ 连续 3 天低于基准 → 卡片同时有 `status=NORMAL` 与 `hints=[belowBaseline]`，排序仍在正常组。
7. 他组织：首页不列、`/projects/:id/*` → `NOT_FOUND`。
8. OD18 全路径：只读账号对一个有草稿的项目——首页卡片近 7 天格、缺报提示、`/days`、`/attention` 均不含草稿存在的任何迹象（与无记录逐字节相同）；提交后出现。
9. 幂等重放：同键同体返回同响应；同键异体 `IDEMPOTENCY_KEY_REUSED`；重放前撤销会员 → 当前拒绝，不回放。
10. 完成 %：设计量未知 / 0 / 累计为空各一例 → “不可计算”，不是 0 %。
11. 快照 C19 / C20：提交后改主工作项与节点计划日，旧快照不变；次日计划草稿未确认时快照 `nextPlan.rows=[]`、`status='draft'`。
12. 缺报 D4：无应报期间版本不提示；期间登记在 T 之后不回溯影响 T 的判断。
13. 规模：100 个 TEST 项目（各 30 个已提交日）首页 < 1 s；分页越界返回空页不报错。
14. ADR D6 矩阵：report / project-status 两模块的方向 × 范围 × 授权 × 路径，由生成器展开；`unmodelled` 项列出（本轮：合同份额）。
